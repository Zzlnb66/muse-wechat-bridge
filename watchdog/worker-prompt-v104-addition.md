# v1.0.4 Worker prompt addition (review round 2 version; production verify-channel is mandatory, replaces all earlier paragraphs)

GPT ruling + review round 2 (production verification, mandatory): report serve process status and receive-channel status as TWO separate lines. For channel recovery, you MUST use the production checker, not manual JSON field checks: run `python3 ~/workspace/wechat-bridge/bridge.py verify-channel` and report its JSON output (recovered, reason, pid, run_id) verbatim in your report. That checker is read-only, never raises, and never compares ISO timestamp strings. It confirms recovery ONLY when: serve.pid exists and the process is alive with a python bridge.py serve cmdline, serve_run.json and channel_status.json are objects, channel status is ok, consecutive_failures is 0 (int, not bool), last_success_ts is not None, process_pid == serve.pid == serve_run.pid, run_id matches between the two files, boot_id matches the current boot_id, and proc_starttime matches the current /proc/<pid>/stat field 22, with serve.pid and proc_starttime unchanged during the check. DELETE the old time rule: do NOT require last_success_ts >= process_started_ts. last_success_ts is human-readable freshness evidence only. If the checker says recovered False, report ONLY the checker's reason: if the process is confirmed running, say 'process recovered, channel pending confirmation' (or the checker's specific reason); if init failed or the process is not running, say 'startup failed / process not running, channel unconfirmed' - NEVER 'process recovered'. Expired wake rule: if the wake payload says serve_down but your check now shows serve alive, this is an EXPIRED wake. Do NOT restart serve, do NOT report it as a new outage, and do NOT send the user a 'actually a false alarm' correction notice; just note it as expired in your report. Re-remind rule: an inbox file that stays in inbox/ is re-woken by the watchdog after 300s from its last wake; if you receive the same file again, do NOT treat it as a new message if you already processed it - skip it by message_id / processed list, and do NOT send a duplicate reply or a duplicate outage/recovery notice to the user. NEEDS_RELOGIN / ret -14 is a login signal, not a channel error, and must never be inferred from channel_status.json alone.

Note: this paragraph is prepended to the existing prompt in ~/hooks/definitions/wechat-bridge-watchdog.json at deploy time; it is not a standalone prompt. It replaces every earlier v1.0.4 Worker paragraph, including any that required last_success_ts >= process_started_ts.
